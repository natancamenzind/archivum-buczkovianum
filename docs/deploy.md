# Test environment runbook

The test environment (US-OPS-01) runs on Render. Everything is declared in `render.yaml`, a Render Blueprint, in the Frankfurt region:

| Resource | Type | Built from | Role |
|----------|------|------------|------|
| `archivum-test` | web service | `deploy/Dockerfile` | gunicorn on `$PORT`. Migrations run as the pre-deploy command. The site is public; only `/admin/` asks for a login. `X-Robots-Tag` comes from Django middleware. |
| `archivum-test-db-v2` | Render Postgres 18, 1 GB disk | — | The database. Reachable only over the private network (`ipAllowList: []`). |

Media are in S3, outside Render. Every variable is described in `deploy/.env.example`.

The test environment has no backups by design; its data is disposable.

The database is PostgreSQL 18, which has no `polish` text search configuration, so search runs with `SEARCH_TS_CONFIG=simple` and does not handle Polish inflection (architecture section 6).

## Setup

1. In the Render dashboard, New → Blueprint, connect the GitHub repo and pick `main`. Render reads `render.yaml` from the repo root.
2. Render lists the resources it will create and asks for every variable marked `sync: false`: `DJANGO_SUPERUSER_USERNAME`, `DJANGO_SUPERUSER_EMAIL`, `DJANGO_SUPERUSER_PASSWORD`, `AWS_STORAGE_BUCKET_NAME`, `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`.

   Render asks only on this first sync. A secret added to `render.yaml` later must be set by hand in the service's Environment tab. `SECRET_KEY` is generated by Render; `DATABASE_URL` and `ALLOWED_HOSTS` are references, so nothing else is typed.
3. Apply. Render creates the database, builds the image, runs every migration in the web service's pre-deploy step, and after the first successful deploy runs `python manage.py createsuperuser --noinput`, which creates the editor account from the `DJANGO_SUPERUSER_*` values.
4. Set the media bucket's CORS rules. The scan viewer fetches PDFs from the bucket with `fetch()` and Range requests, so the bucket must allow the site's origin; images in `<img>` work without it. With a key that may change the bucket's configuration:

   ```bash
   aws s3api put-bucket-cors --bucket <AWS_STORAGE_BUCKET_NAME> --cors-configuration file://deploy/s3-cors.json
   ```

   Run it again after every change to `deploy/s3-cors.json`.
5. Check the site at `https://archivum-test.onrender.com`: it opens without credentials, `/healthz` answers 200, and `curl -sI` shows `X-Robots-Tag: noindex, nofollow`. Log in to `/admin/` as the superuser, and open a typescript: its scan renders.

`ALLOWED_HOSTS` is the service's `onrender.com` hostname, and `CSRF_TRUSTED_ORIGINS` is derived from it. A custom domain needs its own entry in `ALLOWED_HOSTS`, which means changing `render.yaml`, and in `deploy/s3-cors.json`. Render's health check may call the container under another host; `/healthz` answers before host validation, so that does not matter.

## Configuration changes

`render.yaml` is the source of truth. Change it in a PR; after the merge, Render syncs the Blueprint and applies the change. A value changed only in the dashboard is overwritten on the next sync, except variables marked `sync: false`, which Render never touches after the first sync.

## Routine deploy

Merge to `main`. Render builds the new image, runs `python manage.py migrate --noinput` in a one-off container, starts the new version and switches traffic once `/healthz` returns 200.

- If the build or migrations fail, the deploy stops and the old version keeps serving. The deploy's log in `archivum-test` → Events shows why.
- To redeploy the same commit, use Manual Deploy → "Deploy latest commit".

Watch out for migrations that the running version cannot live with (dropping or renaming a column it still reads): the old version keeps serving until the new one passes its health check, against the already migrated database.

## Moving to PostgreSQL 19

`postgresMajorVersion` cannot change once the database exists, so the move is a dump and restore into a new database. Do it once Render offers PostgreSQL 19.

1. **Prepare a PR** that adds a database `archivum-test-db-19` with `postgresMajorVersion: "19"`, points `DATABASE_URL` of `archivum-test` at it and sets `SEARCH_TS_CONFIG` to `polish`. Update US-OPS-01 AC2, architecture section 6 and this runbook to match.
2. **Stop writes and dump.** Suspend `archivum-test` (Settings → Suspend Web Service). In `archivum-test-db-v2` → Networking, add your own IP to the access control list, copy the External Database URL from Connect and dump it with `pg_dump --format=custom` (version 18 client).
3. **Merge.** The sync creates the new database; the deploy migrates it while it is empty.
4. **Restore** the dump into `archivum-test-db-19`, opened the same way, with a PostgreSQL 19 client: `pg_restore --clean --if-exists --no-owner --exit-on-error --dbname "<External Database URL>" <dump>`. Remove your IP from both access control lists and resume `archivum-test`. Then rebuild the search index, since stored vectors keep the configuration they were built with: open the service's Shell and run `python manage.py rebuild_search_index`.
5. **Check** the site, including that "potoku" finds "potok".
6. **Clean up.** After a few days without problems, remove `archivum-test-db-v2` from `render.yaml` and delete it in the dashboard.
