# Test environment runbook

The test environment (US-OPS-01) runs on Render. Everything is declared in `render.yaml`, a Render Blueprint, in the Frankfurt region:

| Resource | Type | Built from | Role |
|----------|------|------------|------|
| `archivum-test` | web service | `deploy/Dockerfile` | gunicorn on `$PORT`. Migrations run as the pre-deploy command. Basic auth and `X-Robots-Tag` come from Django middleware. |
| `archivum-test-db` | Render Postgres 18 | — | The database. Reachable only over the private network (`ipAllowList: []`). |
| `archivum-test-backup` | cron job | `deploy/backup.Dockerfile` | Daily at 03:00 UTC: runs `deploy/backup.sh` once and exits. |

Media and backups are in S3, outside Render. Every variable is described in `deploy/.env.example`.

The database is PostgreSQL 18, which has no `polish` text search configuration, so search runs with `SEARCH_TS_CONFIG=simple` and does not handle Polish inflection (architecture section 6).

For a restore you need, on your own machine, the PostgreSQL 18 client tools (`pg_restore`) and the `aws` CLI with credentials for `BACKUP_BUCKET`.

## Setup

1. In the Render dashboard, New → Blueprint, connect the GitHub repo and pick `main`. Render reads `render.yaml` from the repo root.
2. Render lists the resources it will create and asks for every variable marked `sync: false`:
   - `archivum-test`: `BASIC_AUTH_USER`, `BASIC_AUTH_PASSWORD`, `DJANGO_SUPERUSER_USERNAME`, `DJANGO_SUPERUSER_EMAIL`, `DJANGO_SUPERUSER_PASSWORD`, `AWS_STORAGE_BUCKET_NAME`, `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`.
   - `archivum-test-backup`: `BACKUP_BUCKET`.

   Render asks only on this first sync. A secret added to `render.yaml` later must be set by hand in the service's Environment tab. `SECRET_KEY` is generated by Render; `DATABASE_URL`, `ALLOWED_HOSTS` and the backup job's AWS keys are references, so nothing else is typed.
3. Apply. Render creates the database, builds both images, runs every migration in the web service's pre-deploy step, and after the first successful deploy runs `python manage.py createsuperuser --noinput`, which creates the editor account from the `DJANGO_SUPERUSER_*` values.
4. Check the site at `https://archivum-test.onrender.com`: without credentials it answers 401, `/healthz` answers 200, and `curl -sI` shows `X-Robots-Tag: noindex, nofollow`. Log in to `/admin/` as the superuser.
5. Check the backup after its first run at 03:00 UTC (or use "Trigger Run" on the cron job): its log ends with `Uploaded s3://…/db/<timestamp>.dump`, and the object is in the bucket.

`ALLOWED_HOSTS` is the service's `onrender.com` hostname, and `CSRF_TRUSTED_ORIGINS` is derived from it. A custom domain needs its own entry in `ALLOWED_HOSTS`, which means changing `render.yaml`. Render's health check may call the container under another host; `/healthz` answers before host validation, so that does not matter.

## Configuration changes

`render.yaml` is the source of truth. Change it in a PR; after the merge, Render syncs the Blueprint and applies the change. A value changed only in the dashboard is overwritten on the next sync, except variables marked `sync: false`, which Render never touches after the first sync.

## Routine deploy

Merge to `main`. Render builds the new image, runs `python manage.py migrate --noinput` in a one-off container, starts the new version and switches traffic once `/healthz` returns 200.

- If the build or migrations fail, the deploy stops and the old version keeps serving. The deploy's log in `archivum-test` → Events shows why.
- To redeploy the same commit, use Manual Deploy → "Deploy latest commit".

Watch out for migrations that the running version cannot live with (dropping or renaming a column it still reads): the old version keeps serving until the new one passes its health check, against the already migrated database.

## Restore from backup

Dumps are in `s3://$BACKUP_BUCKET/db/`, named by UTC time (`20261029T030000Z.dump`); the newest 14 are kept.

1. **Stop writes.** Suspend `archivum-test` (Settings → Suspend Web Service) and `archivum-test-backup`. The site is down until step 5.
2. **Open the database temporarily.** In `archivum-test-db` → Networking, add your own IP to the access control list. Copy the External Database URL from Connect.
3. **Fetch the dump and restore.**

   ```bash
   aws s3 ls "s3://$BACKUP_BUCKET/db/"                  # pick a dump
   aws s3 cp "s3://$BACKUP_BUCKET/db/<name>.dump" restore.dump

   DB="<External Database URL>"
   pg_restore --clean --if-exists --no-owner --exit-on-error --dbname "$DB" restore.dump
   ```

4. **Close the database.** Remove your IP from the access control list. The next Blueprint sync would reset it to `ipAllowList: []` anyway, but do not wait for one.
5. **Start the app.** Resume `archivum-test` and `archivum-test-backup`.

Check the site, then delete `restore.dump`. Media is in its own S3 bucket and is not part of the dump.

To run the backup by hand, outside Render, from any machine with bash, `pg_dump` 18 and the `aws` CLI (with the database opened as in step 2):

```bash
DATABASE_URL="<External Database URL>" BACKUP_BUCKET=… AWS_DEFAULT_REGION=eu-north-1 \
  AWS_ACCESS_KEY_ID=… AWS_SECRET_ACCESS_KEY=… deploy/backup.sh
```

## Moving to PostgreSQL 19

`postgresMajorVersion` cannot change once the database exists, so the move is a dump and restore into a new database. Do it once Render offers PostgreSQL 19.

1. **Prepare a PR** that adds a database `archivum-test-db-19` with `postgresMajorVersion: "19"`, points `DATABASE_URL` of both services at it, sets `SEARCH_TS_CONFIG` to `polish`, and changes `FROM postgres:18` to `FROM postgres:19` in `deploy/backup.Dockerfile`. Update US-OPS-01 AC2, architecture section 6 and this runbook to match.
2. **Stop writes and dump.** Suspend both services as in a restore, open `archivum-test-db` and dump it with `pg_dump --format=custom` (version 18 client).
3. **Merge.** The sync creates the new database; the deploy migrates it while it is empty.
4. **Restore** the dump into `archivum-test-db-19` as in a restore, with a PostgreSQL 19 client, then rebuild the search index, since stored vectors keep the configuration they were built with: open the service's Shell and run `python manage.py rebuild_search_index`.
5. **Check** the site, including that "potoku" finds "potok", and the next backup's log.
6. **Clean up.** After a few days without problems, remove `archivum-test-db` from `render.yaml` and delete it in the dashboard.
